# 第一案證據登錄表與推理設計

文件狀態：**可供 Opus 選用、修改的證據素材**；不是已實作的資料表。詳見 [1854 年史實](HISTORY_1854.md) 與 [來源](SOURCES_AND_ASSETS.md)。

## 標示規則

- **[H] 史實**：史料明確記錄的核心事實（不代表道具原件必然存在）。
- **[R] 合理重建**：符合時代且有史實背景，但遊戲內的文件格式、具體文本、事件順序經過創作。
- **[F] 虛構**：人物、對白或整組事件由遊戲創作。
- **[U] 未證／有爭論**：需要更多來源；不能在遊戲中宣告定論。

**每張「遊戲證據卡」可能同時含 H + R**：例如歷史數字屬 H，但以一位不存在的紀錄員於某日交付的紙張呈現屬 R/F。程式欄位不應只存一個真假布林值。

## 第一個真正能玩的推理：E02 + E03

**目標：** 玩家**自己**注意到，啤酒廠暴露於同一街區環境，卻沒有出現同等嚴重的病例；這些工人不使用街泵水。

1. 玩家點擊「病例／街區地圖」→ 獲得 E01。
2. 玩家查看「啤酒廠調查報告」→ 獲得 E02。
3. 玩家查看「啤酒廠取水說明」→ 獲得 E03。
4. 玩家選擇**至少兩項有關證據**，主動建立推論；單純看完三張不會直接揭示答案。
5. 若用 E02 + E03：呈現「**住所／工作地點的距離不是唯一差異，取水來源值得調查**」。這支持後續追查，不代表因果已經完全證實。
6. 若選 E01 + E02：可指出「同區結果不同」是有效觀察，**但還沒有找出造成差異的因素**；允許繼續。
7. 若用無關線索或過強結論，角色以具體疑問提示尚缺哪一類證據；不替玩家直接說出正解。
8. 可取消組合、改判斷、重看卡片與重新遊玩。錯誤推論不是 Game Over。

要避免兩種糟糕設計：**完成全部點擊就自動破案**；或 **先選一個完美預設答案才能推進，沒選對就永遠卡關**。

## 可能的假說卡：設計為可受支持／質疑，不是魔法真理選擇

| 初步解釋 | 應看見的現象 | 玩家能指出的疑點 |
| --- | --- | --- |
| 污濁空氣是唯一決定因素 | 同地點／同時段應有一定類似暴露 | 啤酒廠、濟貧院等近處低病例群值得追查 |
| 直接靠近病人就必定感染 | 風險應主要伴隨接觸與近距離 | 遠方病例與不同飲水習慣需要更細致的解釋 |
| 某種受污染飲水／食物來源 | 住得遠也可能受害；近處飲不同水者可能免受同一暴露 | 為何有人喝過泵水卻沒病？還有資料缺口嗎？ |

注意：**接觸造成污染的食物／水與水源傳播並不互斥**，不能教玩家「人與人之間完全不會傳播」。系統最好比較「這一解釋能否解釋所有觀察」，而不是三選一純對錯。

## 最小資料模型建議（僅示意，非技術強制）

- `Evidence`: `id, title, body, sourceIds, provenanceTags, availableAfter, revisitAllowed`
- `Hypothesis`: `id, statement, support, challenges, limitations`
- `Inference`: `evidenceIds[], claimId, feedback, nextQuestion`
- `CaseState`: `discoveredEvidenceIds[], submittedInferences[], scene, conclusion`

**先硬寫出足夠好玩的三張卡也可以**；只有需要重用時才資料化。不要四天內建立通用推理編輯器、RAG、知識圖譜或 AI 自動裁決系統。
